# 服务器运行手册

本文作为 Linux/Ubuntu 服务器命令速查，沿用部署路径
`/opt/GITHUB-SENTIMENT/github-sentiment`（服务器记录：`115.159.4.52`）。
除 SQL 外，命令均在服务器 Bash 中执行；SQL 在 `mysql>` 中执行。
实际版本与样本名应先查询确认，示例不代表任务已完成。
项目背景见 [README](../README.md)，配置、版本历史、仓库选取与数据口径见 [项目元数据](项目元数据.md)。

## 1. 运行方面的指令

### 1.1 进入项目与准备环境

```bash
cd /opt/GITHUB-SENTIMENT/github-sentiment
source .venv/bin/activate
```

首次部署尚无虚拟环境时：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e .
```

服务器已有 `uv` 时也可执行 `uv pip install --python .venv/bin/python -e .`。
退出已激活的虚拟环境使用 `deactivate`。

### 1.2 配置与启动 MySQL

编辑服务器现有配置，保留数据库与 GitHub 配置：

```bash
vim .env
```

生产环境沿用两个 Compose 文件时，在 `.env` 设置：

```dotenv
COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml
```

`docker-compose.prod.yml` 是服务器私有覆盖文件，仓库中未提供；确认它已存在再使用此设置。
Docker 卷已有数据库的密码须与运行配置一致。

```bash
docker compose up -d mysql
docker compose restart mysql
```

`restart` 按需执行。`docker compose down -v` 会删除数据卷，不用于日常重启。

默认模型配置（按当前代码核对；密钥填入服务器 `.env`）：

```dotenv
LLM_PROVIDER=glm
GLM_API_KEY=填写对应服务的密钥
GLM_BASE_URL=https://open.bigmodel.cn/api/coding/paas/v4
GLM_MODEL=glm-5.3-flash
GLM_REASONING_EFFORT=low
GLM_MAX_TOKENS=8192
GLM_TIMEOUT_SECONDS=180
```

切回 DeepSeek 时设置 `LLM_PROVIDER=deepseek`，并配置 `DEEPSEEK_API_KEY`、
`DEEPSEEK_BASE_URL` 和 `DEEPSEEK_MODEL`。改配置后须启动新进程。

### 1.3 初始化数据库与管理仓库

首次部署或升级后创建缺失结构，兼容字段与 corpus 输入长度回填也由该入口处理：

```bash
python pipeline.py init-db
```

已有大量 corpus 时回填可能耗时，按日志确认完成。此入口不是通用数据库迁移工具。
新增或重新启用仓库、停用但保留历史数据：

```bash
python pipeline.py repo add rust-lang/cargo
python pipeline.py repo enable rust-lang/cargo
python pipeline.py repo disable rust-lang/cargo
```

三条是不同管理操作，按需单独执行。`GITHUB_REPOSITORIES` 仅用于空仓库表的首次导入。

#### 创建与刷新方面情感查询表

升级后先创建缺失表，再生成查询数据：

```bash
python pipeline.py init-db
python pipeline.py refresh-sentiment-facts --batch-size 1000
```

`sentiment_facts` 只保存 `corpus_id`、`repository_id`、GitHub 原文的 `created_at`、
`aspect`、`sentiment`。每个语料/方面一行，`sentiment` 来自标注项的 `class`。
选择规则见 [项目元数据](项目元数据.md#方面情感查询表口径)。

此命令按批读取，在一个事务中全量替换查询表；失败时回滚，旧查询数据保留。
使用现有流水线锁，不能与采集、清洗或标注命令同时运行。
后续新增、修改或删除标注后，再执行刷新命令；当前不会在标注写入时自动刷新。
输出 `scanned_corpus`（选出的成功标注语料数）、`included_corpus`（有方面的语料数）、
`empty_corpus`（空方面语料数）及 `rows`（展开后的方面记录数）。

### 1.4 采集、构建与普通采样

先按每个启用仓库、本次运行的配额采集：

```bash
python pipeline.py collect \
  --max-issues 2000 \
  --max-pull-requests 1000 \
  --max-issue-comments 4000 \
  --max-pr-comments 1500 \
  --max-review-comments 1500
python pipeline.py build-corpus
```

未传的采集类型不限量，`0` 表示本次不写入该类型；达到配额记为 `quota_reached`。
分步执行时先查询采集结果，确认没有失败流再构建 corpus。
更便捷的串联执行见 1.6 节，其 `run` 入口在采集失败时自动跳过后续阶段。

创建普通集，以下采样与标注均使用 `rust-v1`：

```bash
python pipeline.py sample \
  --name rust-v1 \
  --cleaning-version clean-v2 \
  --per-repository 5000 \
  --max-model-input-chars 4000 \
  --seed 20260728
```

`--cleaning-version` 只选择已有 corpus，不重新清洗；字符上限包含 CONTEXT 和 TARGET。
已完成的同名、同参数集合直接复用；更改参数或纳入新增语料时换集合名。

### 1.5 标注指定集合

先小规模验证，再处理该集合全部待标注记录：

```bash
.venv/bin/python -u pipeline.py label --sample rust-v1 --limit 100 --concurrency 5
.venv/bin/python -u pipeline.py label --sample rust-v1 --concurrency 5
```

每条语料一个独立请求；并发按账户额度调整，不传时默认 20，硬上限 500。
失败结果可再次运行同一命令重试；同语料、标签/提示词版本与模型的成功结果（包括空标签）会复用。
仅修改思考强度不会强制重标。

### 1.6 一次运行采集、构建、采样和标注

下面的命令等价于依次执行限量采集、构建 corpus、创建 `rust-v1` 和只标注
`rust-v1`：

```bash
python pipeline.py run \
  --max-issues 2000 \
  --max-pull-requests 1000 \
  --max-issue-comments 4000 \
  --max-pr-comments 1500 \
  --max-review-comments 1500 \
  --sample-name rust-v1 \
  --sample-cleaning-version clean-v2 \
  --sample-per-repository 5000 \
  --sample-max-model-input-chars 4000 \
  --sample-seed 20260728 \
  --label-concurrency 5
```

只运行限量采集、构建 corpus 和采样，不启动 LLM：

```bash
python pipeline.py run \
  --skip-label \
  --max-issues 2000 \
  --max-pull-requests 1000 \
  --max-issue-comments 4000 \
  --max-pr-comments 1500 \
  --max-review-comments 1500 \
  --sample-name rust-v1 \
  --sample-cleaning-version clean-v2 \
  --sample-per-repository 5000 \
  --sample-max-model-input-chars 4000 \
  --sample-seed 20260728
```

#### 不限量运行

以下命令仍然可用，但不传采集上限和采样集时会沿用旧的全量行为：

```bash
# 全量采集、构建全部 corpus，并标注全部未成功标注的非重复语料
python pipeline.py run

# 全量采集和构建 corpus，不执行 LLM 标注
python pipeline.py run --skip-label

# 只执行不设上限的 GitHub 数据采集
python pipeline.py collect

# 标注全部未成功标注的非重复语料
python pipeline.py label
```

为了避免误标注整个候选语料池，生产环境建议始终显式传入 `--sample` 或
`--sample-name`。

### 1.7 按方面配额建立词典集

以下复现历史集合 `rust-all-aspects-v2-10k` 的配置：13 方面各最多 10,000 条，
使用历史 `clean-v1`。它不会重新清洗语料；换成 `clean-v2` 时需换集合名并先构建相应 corpus。
最终总集合按语料 ID 去重，候选不足会报告 `shortage`，候选配额不等于最终标签数量。

```bash
python pipeline.py sample-lexicon \
  --name rust-all-aspects-v2-10k \
  --lexicon lexicon/rules/rust-targeted-v2.json \
  --cleaning-version clean-v1 --seed 20260917 \
  --max-model-input-chars 4000 \
  --quota ownership=10000 \
  --quota type_system=10000 \
  --quota safety=10000 \
  --quota runtime_performance=10000 \
  --quota learning_curve=10000 \
  --quota compile_time=10000 \
  --quota diagnostics_debugging=10000 \
  --quota tooling_documentation=10000 \
  --quota readability_maintainability=10000 \
  --quota api_extensibility=10000 \
  --quota package_manager=10000 \
  --quota libraries_frameworks=10000 \
  --quota community=10000
```

构建成功后，对这个集合进行全量标注：

```bash
.venv/bin/python -u pipeline.py label --sample rust-all-aspects-v2-10k --concurrency 5
```

不传 --limit。这里“全量”是集合内全部待标注记录；同语料、同提示词/模型版本的成功结果会复用。错误、限流或熔断仍按现有标注器处理，应检查完成统计，失败记录可以再次执行同一 label 命令重试。

也可以每个方面建立一个不同名称的集合：每次 `sample-lexicon` 只传该方面的一个 `--quota`，然后 `label --sample`。未指定配额的方面不参与检索；模型始终检查全部 13 个方面，使用 `LLM_PROVIDER` 指定的供应商。

#### 筛选参数

| 参数 | 含义 |
| --- | --- |
| --quota aspect=N | 该方面最多入选N条；可重复指定不同方面，禁止同方面重复 |
| --cleaning-version | 必填，选择数据库已存在的清洗版本；本例沿用历史 clean-v1 |
| --min-target-chars | clean_text 去除首尾空白后的最小字符数，默认1 |
| --max-model-input-chars | 含上下文的最终输入最大字符数，默认4000 |
| --per-repository | 每方面在每个仓库的候选上限；默认不限制 |
| --source-type | issue / pull_request / issue_comment / pr_issue_comment / pr_review_comment，可重复 |
| --repository | 启用的 owner/repo，可重复；默认全部启用仓库 |
| --seed | 确定性选择种子，默认0 |

### 1.8 后台启动与停止

使用 `nohup` 在退出 SSH 后继续标注指定采样集：

```bash
mkdir -p logs
nohup .venv/bin/python -u pipeline.py label \
  --sample rust-all-aspects-v2-10k \
  --concurrency 5 \
  >> logs/pipeline.log 2>&1 &
echo $! > logs/pipeline.pid
```

反斜杠只放在行尾续行，`>>` 追加日志；不要重复启动同一任务。

确认查询节中的 PID 对应本次任务后，发送停止信号：

```bash
kill "$(cat logs/pipeline.pid)"
```


### 1.9 方面内 BERTopic 试验

安装可选依赖（以下为不同安装方式，按需选择）：

在服务器的仓库根目录，使用项目虚拟环境安装可选依赖；若尚未创建 `.venv`，先运行 `python3 -m venv .venv`：

```bash
.venv/bin/python -m pip install -e '.[topics]'
```

如果提示 `.venv/bin/python: No module named pip`，可先向现有虚拟环境安装 pip，再执行上面的命令：

```bash
.venv/bin/python -m ensurepip --upgrade
```

如果服务器已经安装 `uv`，也可以直接向该虚拟环境安装依赖，不要求 `.venv` 中有 pip：

```bash
uv pip install --python .venv/bin/python -e '.[topics]'
```

如果直连 PyPI 下载依赖时超时，可以仅在本次安装中改用清华 PyPI 镜像，并延长 HTTP 读取超时：

```bash
UV_HTTP_TIMEOUT=300 uv pip install --python .venv/bin/python \
  --default-index https://mirrors.tuna.tsinghua.edu.cn/pypi/web/simple/ \
  -e '.[topics]'
```

先生成数据库语料快照；下面的模型、提示词与清洗版本必须在数据库中有成功标注：

```bash
.venv/bin/python -m topic_analysis inspect --model-name glm-5.3-flash \
  --prompt-version aspect-sentiment-zh-v8 --cleaning-version clean-v1 \
  --name source-20260927
```

后台执行 inspect：

```bash
mkdir -p logs
nohup .venv/bin/python -u -m topic_analysis inspect \
  --model-name glm-5.3-flash \
  --prompt-version aspect-sentiment-zh-v8 --cleaning-version clean-v1 \
  --name source-20260927 \
  > logs/topic-inspect.log 2>&1 &
echo $! > logs/topic-inspect.pid
```

fit 必须指定 inspect 快照名；模型名、标签/提示词/清洗版本、语言及文本长度参数须匹配。
先试一个方面与 2,000 条上限：

```bash
.venv/bin/python -m topic_analysis fit --model-name glm-5.3-flash \
  --prompt-version aspect-sentiment-zh-v8 --cleaning-version clean-v1 \
  --snapshot source-20260927 \
  --aspect package_manager --max-docs-per-aspect 2000 --name pilot-package
```

去掉 `--aspect` 和 `--max-docs-per-aspect` 可对全部 13 方面顺序训练。
可用 `--min-topic-size`、`--min-samples`、`--umap-neighbors` 调整聚类。
快照名和运行名已存在（含 `.building`）时换新名字；补采后重新 inspect 创建新快照。

#### 下载并离线使用编码器

若 `fit` 下载模型时出现 `huggingface.co` 网络不可达，PyPI 镜像对此无效。可先确认服务器能否访问第三方模型镜像 `hf-mirror.com`：

```bash
curl -I --max-time 10 https://hf-mirror.com/sentence-transformers/all-MiniLM-L6-v2/resolve/main/modules.json
```

若可达，再把模型下载到仓库内已忽略的 `data/models/`：

```bash
mkdir -p data/models
.venv/bin/python - <<'PY'
from huggingface_hub import snapshot_download

snapshot_download(
    "sentence-transformers/all-MiniLM-L6-v2",
    local_dir="data/models/all-MiniLM-L6-v2",
    allow_patterns=["*.json", "*.txt", "*.safetensors"],
    endpoint="https://hf-mirror.com",
)
PY
```

镜像不可达时按 [模型离线准备](模型离线准备.md) 在本地下载并传到服务器。
在服务器验证模型可离线加载：

```bash
HF_HUB_OFFLINE=1 .venv/bin/python -c "from sentence_transformers import SentenceTransformer; model = SentenceTransformer('data/models/all-MiniLM-L6-v2', device='cpu', local_files_only=True); print(model.encode(['model ready']).shape)"
```

验证完成后后台运行 fit：

```bash
mkdir -p logs
HF_HUB_OFFLINE=1 nohup .venv/bin/python -u -m topic_analysis fit \
  --model-name glm-5.3-flash \
  --prompt-version aspect-sentiment-zh-v8 --cleaning-version clean-v1 \
  --snapshot source-20260927 \
  --aspect package_manager --max-docs-per-aspect 2000 \
  --embedding-model data/models/all-MiniLM-L6-v2 --name pilot-package-local \
  > logs/topic-fit-pilot-package-local.log 2>&1 &
echo $! > logs/topic-fit-pilot-package-local.pid
```

当前流程使用 CPU，先检查资源与结果再扩大样本；产物及统计口径见 [项目元数据](项目元数据.md)。

### 1.10 可选：配置 MySQL 快捷命令

在 `~/.bashrc` 中加入以下函数，之后仍需在项目目录调用：

```bash
mysqlcli() {
  docker compose exec mysql sh -lc \
    'exec mysql --default-character-set=utf8mb4 -u"$MYSQL_USER" --password="$MYSQL_PASSWORD" "$MYSQL_DATABASE"'
}
mysqlroot() {
  docker compose exec mysql sh -lc \
    'exec mysql --default-character-set=utf8mb4 -uroot --password="$MYSQL_ROOT_PASSWORD"'
}
```

保存后执行 `source ~/.bashrc`；查询时使用 `mysqlcli`，管理权限时使用 `mysqlroot`。

### 1.11 启动前端查询 API

后端新增独立只读服务，不需要 GitHub 或 LLM 密钥：


[Ubuntu 部署说明](https://github.com/Wangyuhan29/Developer-Voice/blob/main/docs/ubuntu-deployment.md)。

监听 127.0.0.1:8000。本机开发按 [SSH 开发联调](https://github.com/Wangyuhan29/Developer-Voice/blob/main/docs/ssh-development.md)
分别启动隧道与 Vite，生产部署继续通过 Nginx 代理 `/api/v1`。

### 2.4 采集结果

#### 各仓库的五类原始数据量

Issue、PR、Issue comment 分别存放在三张表中；PR 普通评论和 Review comment 共用
`pr_comments`，通过 `comment_type` 区分。

```sql
SELECT
    r.full_name,
    r.enabled,
    COALESCE(i.issue_count, 0) AS issue_count,
    COALESCE(p.pull_request_count, 0) AS pull_request_count,
    COALESCE(ic.issue_comment_count, 0) AS issue_comment_count,
    COALESCE(pc.pr_issue_comment_count, 0) AS pr_issue_comment_count,
    COALESCE(pc.pr_review_comment_count, 0) AS pr_review_comment_count,
    COALESCE(i.issue_count, 0)
        + COALESCE(p.pull_request_count, 0)
        + COALESCE(ic.issue_comment_count, 0)
        + COALESCE(pc.pr_issue_comment_count, 0)
        + COALESCE(pc.pr_review_comment_count, 0) AS total_raw_count
FROM repositories AS r
LEFT JOIN (
    SELECT repository_id, COUNT(*) AS issue_count
    FROM issues
    GROUP BY repository_id
) AS i
    ON i.repository_id = r.id
LEFT JOIN (
    SELECT repository_id, COUNT(*) AS pull_request_count
    FROM pull_requests
    GROUP BY repository_id
) AS p
    ON p.repository_id = r.id
LEFT JOIN (
    SELECT repository_id, COUNT(*) AS issue_comment_count
    FROM issue_comments
    GROUP BY repository_id
) AS ic
    ON ic.repository_id = r.id
LEFT JOIN (
    SELECT
        repository_id,
        SUM(comment_type = 'issue_comment') AS pr_issue_comment_count,
        SUM(comment_type = 'review_comment') AS pr_review_comment_count
    FROM pr_comments
    GROUP BY repository_id
) AS pc
    ON pc.repository_id = r.id
ORDER BY r.full_name;
```

#### 指定采样集的标注进度

`pending_count` 包括从未尝试和标注失败、等待重试的语料。

```sql
    COALESCE(SUM(a.status = 'failed'), 0) AS failed_count,
    SUM(a.id IS NULL OR a.status <> 'succeeded') AS pending_count,

        / NULLIF(COUNT(*), 0),
        2
    ) AS completion_percent
FROM corpus_sample_items AS i
JOIN corpus_sample_sets AS s
    ON s.id = i.sample_set_id
LEFT JOIN llm_annotations AS a
    ON a.corpus_id = i.corpus_id
    AND a.taxonomy_version = @taxonomy_version
    AND a.prompt_version = @prompt_version
    AND a.model_name = @model_name
WHERE s.name = @sample_name;
```

#### 标签与情感分布

MySQL 8 使用 `JSON_TABLE` 展开成功结果。未提及的标签不会输出，也不能计入
`neutral`。

```sql
SELECT
    labels.aspect,
    labels.sentiment_class,
    COUNT(*) AS sample_count
FROM corpus_sample_items AS i
JOIN corpus_sample_sets AS s
    ON s.id = i.sample_set_id
JOIN llm_annotations AS a
    ON a.corpus_id = i.corpus_id
JOIN JSON_TABLE(
    a.parsed_result,
    '$.annotations[*]'
    COLUMNS (
        aspect VARCHAR(64) PATH '$.aspect',
        sentiment_class VARCHAR(20) PATH '$.class'
    )
) AS labels
    ON TRUE
WHERE s.name = @sample_name
  AND a.taxonomy_version = @taxonomy_version
  AND a.prompt_version = @prompt_version
  AND a.model_name = @model_name
  AND a.status = 'succeeded'
GROUP BY labels.aspect, labels.sentiment_class
ORDER BY labels.aspect, sample_count DESC;
```
