# 用 Codex 标注5–10万条的可行性（2026-09-17）

> 历史评估：保留 2026-09-17 的方案、价格与工期假设；本次仅迁移，未重新核验外部产品、价格或额度。当前项目配置见 [项目元数据](../../项目元数据.md)。

## 结论及评估时的实现边界

技术上可行。直接使用 Codex 适合先导标注、疑难复核和带断点的分批作业；如果要求可预测的全量吞吐和费用，更适合由 Codex 开发、检查流程，再用模型 API 批处理。截至评估日期，项目 `label` 入口支持GLM和DeepSeek，已有并发、重试、结果校验、成功结果复用和版本隔离；尚无 Codex CLI 批次适配器、OpenAI Batch 提交/回收或外部结果导入入口。本节是可行性评估，没有启动全量标注。

“Codex”是运行标注任务的工具环境，模型需要另行明确。原评估记录所用模型为 GPT-6 Astra；也可以在可用模型中试验成本更低的候选，但不应预设更强模型就一定符合本项目标签口径。此前250条复核是助手语义复核，不是独立人工金标准，不能据此宣称 Codex 达到某个准确率。

## 直接使用 Codex 账户

官方支持 `codex exec` 非交互运行、`--output-schema` 约束最终 JSON、`--json` 记录事件与 usage、`-o` 保存最终结果。因此可将已冻结数据切成独立批次，程序逐批调用并校验结果。[OpenAI 非交互文档](https://learn.chatgpt.com/docs/non-interactive-mode)

建议试验每批10–25条，额外设置输入 token 上限，避免长文本批次过大。每条结果必须带 corpus_id，每批固定模型、标签定义、提示词及清洗版本；输出后检查所有ID恰好出现一次、标签合法且每方面最多一次，空数组是合法标注，缺失结果是失败。保存批次清单、输入哈希、原始响应、失败状态和已完成ID；独立新会话避免旧批次干扰，重试只处理失败批次/缺失条目。JSON事件流与最终标签JSON是两种文件，不可混用。

5万/10万条按25条一批，分别需要2000/4000次调用。若试跑测得每批30–90秒，串行纯运行时间约为17–50小时/33–100小时；这里30–90秒只是演算假设，尚未测量。实际还要加限流、额度等待、失败重试和复核时间。并发只能改善有可用额度时的吞吐，不能扩大账户总额度。

Codex 的消耗随模型、上下文、推理、工具与缓存变化，官方消息量是估计值，且可能同时受五小时和周额度限制。因此不能用“剩余百分比”或套餐消息数保证能完成多少条，也不能把订阅额度折算为下表API美元成本。对当前账户能否完成及需要几天，必须先记录试跑前后额度、usage、耗时和成功数。[Codex 使用限制](https://learn.chatgpt.com/docs/pricing#what-are-the-usage-limits-for-my-plan)

## API批处理的体积、费用和工期

离线测量现有v8提示词：6380字符，在 `o200k_base` 编码下约2580 tokens；历史4884条合格文本的单条用户JSON平均138 tokens，P95为456 tokens。这里只统计文本编码，未包含JSON Schema、消息封装、Codex环境提示词或推理输出，也不能代表词典候选的真实长度。记录见 [体积测量](labeling-size-estimate.json)。正式预算应由试跑返回的实际usage替换。

下面按每条独立请求、2800输入tokens、100–1000计费输出tokens（包括推理）计算美元情景成本；不使用缓存折扣，不含重试、人工复核、税及额外服务费用。100–1000是敏感性分析假设，不是模型输出保证；尤其高推理强度可能超过该范围。

| API模型 | 普通输入/输出单价（美元/百万tokens） | 5万条普通API | 10万条普通API | 5万条Batch | 10万条Batch |
| --- | --- | ---: | ---: | ---: | ---: |
| GPT-5.6 Luna | 0.20 / 1.20 | 34–88 | 68–176 | 17–44 | 34–88 |
| GPT-5.6 Terra | 2.00 / 12.00 | 340–880 | 680–1760 | 170–440 | 340–880 |
| GPT-6 Astra | 10.00 / 50.00 | 1650–3900 | 3300–7800 | 825–1950 | 1650–3900 |

公式：`N × (平均输入tokens × 输入单价 + 平均计费输出tokens × 输出单价) / 1,000,000`，Batch再乘0.5。价格核对自[OpenAI API价格页](https://developers.openai.com/api/docs/pricing)，按短上下文、普通处理计价；模型支持Batch与结构化输出分别见 [Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna)、[Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra)、[Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)。低价只表示可作为试验候选，不代表已验证能替代Astra的质量。

Batch官方限制为每批最多50000请求、文件最多200MB，还受每模型排队输入token额度约束；处理窗口为24小时，未完成请求可能过期，需从错误文件识别并重试。输入和输出顺序不保证相同，应按custom_id关联。[Batch官方文档](https://developers.openai.com/api/docs/guides/batch)

本地按完整提示词构造的示意请求平均约12.2KB，5万条就约610MB，不能因为请求数未超50000就全放进一个文件。建议每个上传文件至多5000条并额外按实际UTF-8字节数切分，约61MB/文件；5–10万条对应约10–20个文件。一批5000条按2800输入tokens约占1400万排队tokens，如果账户排队额度更小，必须进一步切分并逐批提交。24小时是单批处理窗口，不能推断全部任务必在24小时完成；项目工期应按可同时排队规模、过期重试和验收轮次计算。

## 建议的质量验收和数据配比

1. 先冻结500–1000条先导集，包含随机背景、13方面候选、多方面、neutral、空标签、引用/日志和上下文依赖案例。建立双人独立标注及分歧裁决的人工金标准；稀少方面另补案例，至少积累约30–50个真阳性后再初步评估。词典不命中的随机文本也必须标注，才能发现漏召回。
2. 对同一先导集比较Codex目标模型与现有DeepSeek；词典命中及旧模型标签不放入标注输入。分别报告每方面precision/recall/F1、macro/micro-F1、方面+情感端到端F1、neutral被漏为空的比例、无标签误报率及样本支持数。多次同模型一致、结构合法、旧模型一致都不等于正确。
3. 可把“总体方面macro-F1≥0.85、关键方面recall≥0.80、结构有效率≥99.9%”作为待团队确认的试验门槛，不能视为已达到的指标；小样本需报告置信区间，低频类别单独补测。先锁定口径，再在独立保留集验收，避免边改规则边用同一集合报告最终性能。
4. 对5–10万条输入，建议先预留30%–50%随机背景，其余用词典补足方面覆盖；具体配额由先导有效率反推。训练集允许富集，估计总体比例和最终测试集要独立随机抽取，并按父Issue/PR及重复文本分组隔离。社区等不足类保持实际shortage，不放宽到无关内容凑数。多方面重叠后按去重并集计算最终条数。
5. 全量运行保存逐条来源、文本/输入哈希、模型、提示词/标签版本、执行批次与原始结果；随机抽查5%–10%，优先复核模型分歧、稀少类和边界案例。随机人工抽查必须包含双方都输出空的样本，避免只审分歧而遗漏共同错误。自动标注作为银标准训练数据，人工测试集单独保留。

如果目标是“5–10万条非空有效样本”而非“送模型5–10万条”，调用规模还要除以有效率。例如有效率40%时，需要约12.5–25万条输入，费用和时间约扩大2.5倍；40%只是演算假设，不能把本次14.5%的词典命中率当成标注有效率。

建议优先用Codex做先导与疑难复核，并以实测决定是否全量。若较低成本模型通过人工保留集验收，可用它批量标注，再对不确定案例和随机样本使用更强模型/人工复核；如果目标是坚持全量Codex，也能按上述独立分批流程实现，但目前尚不能承诺账户额度和完成日期。
