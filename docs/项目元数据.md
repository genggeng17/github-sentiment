普通采样集的成员不可变，但不等于冻结了整个数据库。词典集保存扫描 ID 上界、
词典/输入哈希和选择配置；源字段后来修改仍可能影响重建。
严格复现应保留冻结导出及校验值，训练/测试按父 Issue/PR 和重复文本分组隔离。


### 方面情感查询表口径

`sentiment_facts` 是由 `llm_annotations` 生成的查询快照，包含以下五个字段：

| 字段 | 含义 |
| --- | --- |
| `corpus_id` | 语料 ID，与 `aspect` 组成主键 |
| `repository_id` | 对应原文所属仓库 ID |
| `created_at` | GitHub 原文创建时间，沿用原始表的 UTC 无时区 datetime |
| `aspect` | 标注方面，去掉首尾空白，空值不入表 |
| `sentiment` | 标注项 `class`，为 positive、neutral 或 negative |

每个 `corpus_id` 只选最新成功标注，按 `updated_at` 降序、`id` 降序决定新旧，
不按提示词或模型的版本字符串排序。单版本、两版本、更多版本均按同一规则处理；
失败版本不替代成功版本。选定结果为空标签时不回退到旧版非空标签。
非空结果按方面展开，一条语料可对应多行；跨方面累加得到提及数，不是去重讨论数。
非空方面若出现无效情感、重复方面或缺失来源，刷新失败并回滚，避免生成不完整数据。

本表不额外限制语言、采样集、清洗版本、仓库启用状态或 `duplicate_of_id`，
也不合并不同 `corpus_id` 的同源内容版本。范围是数据库内满足上述规则的 LLM 标注语料，
不代表全部原始讨论。原始标注版本保留在 `llm_annotations`，本表不保存版本字段。
刷新命令及 SQL 示例见 [运行手册](运行手册.md)。

只读 HTTP API 前缀为 `/api/v1`，按 GitHub 创建时间（UTC 月份）查询。
页面语料卡片按 `corpus_id` 去重，方面画像及趋势按查询表行数计数。
正面和负面语料卡片可重叠；模型/标签版本未保存到查询表，不在 API 中推测版本。
Topic 关键词等继续为前端 mock，具体响应约定见
[前端 API 契约](https://github.com/Wangyuhan29/Developer-Voice/blob/main/docs/API_CONTRACT.md)。

2026-10-07 首次服务器刷新成功：选取最新成功标注的语料 158,594 条，
其中非空方面语料 56,388 条、空方面语料 102,206 条，展开为 74,911 行。

### 50 个目标仓库与优先度

候选仓库按以下原则筛选：

- 仓库公开、非 Fork、未归档、启用 GitHub Issues，且主语言为 Rust；
- 近期仍有维护活动，Issue、PR、普通评论和 Review comment 具有可采集性；
- 讨论能够覆盖 `rust-aspects-v2`，而不只是具体产品 Bug；
- 仓库组合覆盖语言、工具链、并发网络、Web、数据库、Wasm、GUI、嵌入式和终端工具；
- 优先选择具有解释性讨论、API 权衡、性能分析、安全性讨论和用户体验反馈的项目；
- 避免仅按 Star 或数据量选择，降低机器人、模板、日志和单一业务问题造成的语料污染。

优先度表示建议的接入顺序，而不是项目质量排名：

- **P0（核心）**：标签命中预期最高，优先完成历史回填和持续增量采集；
- **P1（重点扩展）**：能显著补充领域和标签覆盖，在 P0 稳定后分批启用；
- **P2（补充观察）**：领域代表性强，但产品问题或专用场景可能稀释 Rust 情感信号；
  应先小规模采集并人工评估非空标签率。

### 启用策略

50 个仓库不应一次性全量回填。按既有部署记录，生产服务器为两核 4 GB，且 GitHub API 存在主限流和
次级限流，建议：

1. 保持数据库中已启用的仓库持续增量采集；
2. 先对新增 P0 仓库做小规模采集和人工抽检，再逐个历史回填；
3. P0 稳定后按领域分批接入 P1，每批 3～5 个仓库；
4. P2 每个仓库先抽取 200～500 条语料，统计非空标签率、机器人比例、纯日志/代码比例；
5. 只有能补充现有标签或领域缺口的 P2 仓库才长期启用；
6. 训练集继续使用每仓库上限，并进一步监控来源类型、时间和标签分布，避免超大仓库
   主导样本。

优先度和候选池应至少每季度复核一次；仓库归档、迁移、长期停更或有效标签率过低时，
可在数据库中停用，但保留历史数据和游标。

`GITHUB_REPOSITORIES` 只在 `repositories` 表为空时由 `init-db` 首次导入；之后修改
环境变量不会替换数据库白名单。管理与查询命令见 [运行手册](运行手册.md)。


## 4. 标签体系与标注口径

当前标签体系版本为 `rust-aspects-v2`，包含 13 个方面：

| 类别 | 标签 | 含义 |
| --- | --- | --- |
| Language | `ownership` | 所有权、借用、生命周期、移动语义和借用检查器 |
| Language | `type_system` | 静态类型、类型推导、泛型和 trait |
| Language | `safety` | 内存安全、线程安全、数据竞争和 unsafe 代码 |
| Language | `runtime_performance` | 运行速度、延迟、吞吐量、内存和 CPU 效率 |
| Experience | `learning_curve` | Rust 的入门难度、理解成本和掌握时间 |
| Experience | `compile_time` | 初次构建、增量编译、重新编译和 CI 构建速度 |
| Experience | `diagnostics_debugging` | 编译错误、修复建议、调试和问题定位体验 |
| Experience | `tooling_documentation` | IDE、Clippy、rustfmt、教程和 API 文档质量 |
| Engineering | `readability_maintainability` | 代码的可读性、可理解性、可修改性和可维护性 |
| Engineering | `api_extensibility` | API 的直观性、组合性、复用性和扩展能力 |
| Ecosystem | `package_manager` | Cargo、依赖解析、版本、workspace、feature 和发布体验 |
| Ecosystem | `libraries_frameworks` | 第三方库和框架的质量、成熟度及领域覆盖 |
| Ecosystem | `community` | 社区活跃度、交流氛围、维护者响应和协作体验 |

每个已提及方面使用一种情感类别：

- `negative`：明确负面
- `neutral`：明确提及但无明显褒贬
- `positive`：明确正面

### 核心标注原则

- 当前提示词版本为 `aspect-sentiment-zh-v8`，标签体系仍为 `rust-aspects-v2`。
- 先判断目标作者是否实质讨论某方面，再独立判断情感；机制说明、具体问题和设计建议
  可以标为 `neutral`，关键词或机械提及本身不足以成立方面。
- 明确的使用困难、负面影响或改进收益可以表达情感，不要求出现情绪词。
- 上下文用于理解；只有目标作者明确采纳的命题才可归于作者，不自动继承标题或引用的情感。
- 不将具体项目 Bug 强行归入 Rust 标签体系。
- Cargo 相关体验归入 `package_manager`；普通库 Bug 不自动归入
  `libraries_frameworks`。
- 程序运行性能、编译速度和工具响应速度分别归入对应标签。
- 标注结果保留标签体系、Prompt、模型和原始语料版本，便于追溯与重新标注。

## 5. 词典集选择与存储

每方面独立在符合规则与筛选条件的记录中按种子选择，不偏向数据库返回的前N条。可选每仓库上限也是按方面生效，合并集在某仓库的总数可能更高。

同一条语料可以计入多个方面的配额，最终总集按 corpus_id 去重，只送一次标注，因此总条数可能小于配额之和。输出同时记录每方面 requested/eligible/selected/shortage、最终 selected 和 overlap_selections；后者是合并时去掉的重复入选次数。

某方面候选不足时保留实际数量、明确报告 shortage，不用无关语料凑数。候选配额不保证最终方面标签数量；若有效标签仍不足，使用新集合名进行后续补充。

### 存储与复现

第一版按当前需求简化为一个新增表，无需先搭建通用的三表检索平台：

- corpus：继续存一份对应版本的正文。
- corpus_sample_sets.stats.selection_config：冻结完整词典、词典哈希、匹配器版本、方面配额、各方面过滤参数和仓库清单；stats还保存清洗版本、种子、扫描ID上界和完成统计。
- corpus_sample_items：直接保存去重后的独立词典集成员。
- lexicon_sample_hits：按(sample_set_id, corpus_id, candidate_aspect)唯一，保存命中规则、clean_text中的Unicode字符位置、匹配文字、内容哈希和输入哈希；selected_for_quota区分“计入该方面配额”与“入选文本顺带命中了该方面”。
- llm_annotations：仍存模型真正输出的标签，使用 aspect-sentiment-zh-v8 版本，不覆盖v7。

只为最终入选语料存命中明细，未入选候选保留计数，避免在百万条池中持久化大量中间命中。每方面的实际入选成员可通过 lexicon_sample_hits 的 candidate_aspect 和 selected_for_quota=true 查询。

为兼容现有样本集结构，词典集 per_repository_limit 旧列写入总配额之和作为总上界；实际每方面限制以 selection_config.filters 为准。selection_config同时阻止随机集与词典集同名混用。

完成的同名集合、相同参数直接复用；修改词典、配额、过滤条件或仓库清单需换集合名。捕获到的失败会标为failed，再运行时清除半成品并重新扫描；硬中断可能留下building状态，应确认原进程已结束后处理该状态，不能并发使用同名集合。

ID上界防止扫描时把后来插入的记录纳入，本程序不冻结数据库快照；源数据或清洗字段后来修改会影响重新构建结果。哈希用于追溯，当前标注入口尚不自动校验命中时哈希；实验需要严格复现时，应在采集/清洗停止更新期间构建并标注，另存冻结导出。

词典集可以用于补足训练覆盖，但不能混入随机集估计总体比例；训练/测试划分应按父Issue/PR及重复文本分组。

匹配规则 `all` 中的正则必须在 TARGET 的同一段落内同时出现，各条规则之间为“或”。
匹配忽略大小写，屏蔽围栏代码和引用，不检索 CONTEXT；内联代码仍可参与检索。
词典仅生成候选，不决定方面及情感标签，也不向 LLM 提供候选方面提示。

每方面的 `filters` 可覆盖公共筛选参数：`min_target_chars`、`max_model_input_chars`、
`per_repository_limit`、`source_types`、`repository_names`。
`max_model_input_chars` 和 `per_repository_limit` 可设为 `null` 表示该方面不限。
实际词典必须有非空规则列表；调整规则或过滤条件后使用新集合名。


## 6. 主题分析口径与产物

`topic_analysis` 从成功标注的英文语料中，在每个已确认方面内部运行 BERTopic。
同一语料可进入多个方面，情感不参与聚类，聚类结束后才用于统计。
它是独立批次试验，尚未接入每周流水线；嵌入、UMAP、HDBSCAN 均使用 CPU。

`inspect` 从 MySQL 流式读取并生成 `data/topics/snapshots/<name>/` 下的
`documents.jsonl`、`manifest.json`，保留仓库和来源原始创建时间。
`fit` 必须指定已有快照，不再访问数据库；模型名、标签/提示词/清洗版本、语言和
文本长度参数必须与快照一致。快照与运行目录均拒绝复用已有名称（包括 `.building`）。

运行目录 `data/topics/<name>/` 的主要产物：

| 产物 | 内容 |
| --- | --- |
| `manifest.json` | 配置、快照/输入校验值、依赖版本、样本数量、主题代表词与离群比例 |
| `topics.csv`、`review.csv` | 主题及代表文本，后者包含 GitHub 原文链接 |
| `assignments.csv` | 逐条方面、子主题及情感 |
| `topic_sentiment.csv` | 主题与情感统计 |
| `topic_time_sentiment.csv`、`topic_repository_sentiment.csv`、`topic_time_repository_sentiment.csv` | 时间、仓库及其组合统计 |
| `models/`、`encoder/` | BERTopic 模型与本次编码器 |
| `embeddings.npy`、`embedding_corpus_ids.json` | 共享向量及语料 ID 对应关系 |

`share_within_*` 的分母是对应方面在该月份/仓库的全部入选语料（含 `-1` 离群项）。
情感拆为多行，同一主题的总体占比需对三类情感求和；带采样上限时只描述入选样本。
词典富集语料的趋势不能直接推断 GitHub 全体讨论的总体趋势。
未达最小语料数的方面记为 `insufficient`。

## 8. 用量日志字段

`[LLM_USAGE]` 后为单行 JSON；日志不包含密钥、语料正文或推理文本。

| 字段 | 含义 |
| --- | --- |
| `event` / `status` | start、progress、final；running、completed、failed 或 cancelled |
| `run_id` / `model` / `sample_set_id` | 任务、模型与集合；直接调用标注器时自动生成日志任务 ID |
| `completed` / `succeeded` / `failed` | 本次已记录结果、成功、失败数量；是累计值 |
| `in_flight` / `elapsed_seconds` | 正在执行的语料请求数与本次已运行秒数 |
| `input_tokens` / `output_tokens` / `total_tokens` | 已知输入、输出与总用量；缺少 total 时用已知输入加输出 |
| `reasoning_tokens` | 输出的推理子项，不能重复加到 total；未报告为 null |
| `cache_hit_tokens` / `cache_miss_tokens` | 输入的缓存拆分，不能重复加到 total |
| `http_attempts` / `retries` | 已开始的 HTTP 尝试（含重试）、已记录结果携带的重试次数 |
| `usage_responses` / `missing_usage_responses` | 有有效 usage / 无有效 usage 的 JSON 响应数 |
| `output_usage_responses` / `reasoning_usage_responses` | 返回输出 / 推理计数的响应数 |

截断、空内容、非法 JSON 或校验失败的响应只要返回 usage，也会计入用量。
未返回计数的请求不计入未知消耗，因此部分累计数不代表账单全量。
强杀进程、机器掉电无法保证生成 final；更新代码后需重启进程才有新增日志字段。
